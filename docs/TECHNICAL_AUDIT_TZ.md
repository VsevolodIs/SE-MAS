# TutorFlow AI / SE-MAS — техническое ревью по ТЗ преподавателя

**Аудируемая база:** загруженный архив `SE-MAS-main (3).zip` от 10.11.2026. **Статус:** аудит и набор исправлений в отдельной копии, НЕ утверждение о полной готовности к защите. Архив входной версии не изменён.

## Вердикт технического рецензента

Проект содержит рабочую архитектуру LangGraph, локальный вызов Ollama, SymPy-инструмент, SQLite, синтетическую RecSys и бенчмарки. Однако исходная версия **не удовлетворяла в полном объёме** ключевым требованиям ТЗ к независимой проверке, безопасной изоляции, памяти, непрерывному мониторингу и системе оценки. Несколько механизмов создавали ложную видимость подтверждённой корректности. Некоторые были исправлены здесь; оставшиеся требуют отдельных задач, реальных E2E проверок и экспериментальных доказательств.

ТЗ требует: минимум три попробованные LLM и выбор движка, разных семейств модели-исполнителя и валидатора, изолированную среду, собственные skills и семантически наполненные Markdown-файлы, 2–3 слоя памяти, evals по всем категориям, observability (метрики, логи, трейсы, алерты и траектории), 7 C4-диаграмм и sequence flow. Также отдельно назван «Jev-like Model» без технической спецификации. Утверждать реализацию всего этого сейчас нельзя.

## 2. Код по слоям: строгая оценка

### 2.1 Graph / AgentState / Orchestration

**Факт:** есть единый LangGraph workflow и условная маршрутизация между `coordinator → student_profile → {solution_checker, solver_agent, generator, safety} → validator/save`. Требование к связанной мультиагентной системе **частично выполняется**.

**Риск:** `route_task` зависит от набора фраз. В тестовой выборке 42/42 согласованы после доработки, но контрпримеры с новой морфологией, смешанными намерениями и prompt injection ещё не охвачены. Установить вероятность ошибки маршрута по 42 специально подобранным фразам нельзя. Нет confidence, нет маршрута `UNKNOWN`, нет подтверждения семантики независимой моделью.

**Преподаватель спросит:** «Чем отличается агент от промпта? Почему `multi_step`, `clarify` и `personalize` — одна генераторная нода?». Честный ответ: это режимы одного генератора, а не три независимых агента. Агентность обеспечивается orchestration и отдельными solver/checker/validator/safety, инструментами и состоянием, а не количеством названий.

### 2.2 Model routing / независимая валидация

**Факт:** исполнитель генератора `qwen2.5:3b`, решатель `llama3.2:3b`. В проекте есть бенчмарки нескольких других моделей, но решение о выборе не реализовано как policy/конфигурационный профиль. Обновлённый валидатор выбирает другое семейство относительно task model и отказывает при конфликте.

**Риски:** нет доказанного качества «LLM-as-a-Judge»: парсинг вердикта не исключает неверных оценок, нужна эталонная разметка, независимая выборка, confusion matrix, agreement/доля `manual`, human audit. Валидатор для решения ученика с неподдерживаемым форматом отдаёт **предварительное мнение**, не `is_correct=True`.

**Следующий обязательный этап:** собрать размеченные 42+ кейса с ручными вердиктами и сравнить judge с эталоном по типам/сложностям.

### 2.3 SymPy / sandbox

**Изменено:** вычисление в subprocess, тайм-аут приводит к завершению дочернего процесса, ограничены длина и допустимые идентификаторы/символы на входе. Комплексные корни исключаются в школьной действительной области; запрещённые корни ОДЗ отфильтровываются.

**Но:** по ТЗ требуются реально обоснованные границы изоляции. Дочерний Python-процесс наследует полномочия пользователя, доступ к диску и сети. `sympy.sympify` остаётся внутри worker. Нет OS memory cap/CPU quotas, read-only FS, user namespaces, seccomp, gVisor/Kata, VM/MicroVM. Демо нельзя называть безопасной sandbox-изоляцией продакшен-уровня.

**Для закрытия:** выбрать и развернуть исполняющую среду с отдельным непривилегированным пользователем, запретом сети, лимитами CPU/RAM, read-only FS, tmpfs, внешним watchdog; для Windows удобно сравнить Linux VM + gVisor/Kata/Firecracker и Docker Sandboxes. Проверить на контролируемых «тяжёлых» выражениях и фиксировать продолжительность/память. См. актуализированное `docs/sandbox_isolation.md`; остаются незакрытые OS-level требования.

### 2.4 API / Privacy

**Изменено:** универсальный endpoint, явный контракт Pydantic и отсутствие догадки о верности через `math_verified`. Публичный endpoint пока не связывает запрос с реальными персональными профилями.

**Открыто:** нет JWT/OIDC, проверок ролей, ownership студента, секретов, rate limiting, квот на LLM, аудита административных операций. Пробный отказ модели раскрыть чужие данные не доказывает защищённости БД. Нельзя открывать API во внешний интернет.

### 2.5 Memory

**В исходном проекте:** `AgentState`, SQLite `students`, `session_messages`, `assignments`, `lessons`. Обновлено: короткая история снова попадает в генератор для **внутренних** сессий; сессии теперь не смешиваются через общий `default_session`; соединения с SQLite всегда закрываются.

**Не реализовано:** достоверное инкрементальное обновление `weak_topics` после оценок, учёт времени, устранение конфликтов, семантический поиск L3, API удаления данных и согласие на хранение. Стабильный профиль ученика нельзя безопасно основывать только на имени.

**ТЗ:** 2–3 уровня памяти + актуализация. Существующие уровни L1/L2 — начало, не полное выполнение.

### 2.6 Recommendation (Two-Tower)

**Факт:** модель Two-Tower и Recall/HitRate/Precision@10 есть; запуск и оценки — на синтетических взаимодействиях. В `generate_math_interactions()` выбираются `fav_topics`, но эта переменная не влияет на генерацию взаимодействий. Значит, симуляция фактически не проверяет подбор по предпочтительным темам. Модель не связана с `generator_node` и API.

**Преподаватель спросит:** «Рекомендации из Two-Tower реально используются? Что рекомендовано конкретному ученику на основе реальных данных?». Сейчас честный ответ: экспериментальный прототип, не production-персонализация.

**План:** получить реальные обезличенные/синтетические, но осмысленно смоделированные компетенции, обеспечить отсутствие leakage во временном train/test, сравнить с random/popular/topic baseline, воспроизводимость seed, показать интеграцию `recommend(student_id, eligible_tasks)` в граф.

### 2.7 Evals

**Факты:** три LLM сравнивались по TTFT/TPS/длительности; есть 42 сценария датасета и интеграционные отчёты. Метрики completed/`APPROVED` не равны математической точности.

**Исправлено:** `audit_dataset_routes.py` без Ollama (42/42 на данной выборке); `run_graph_dataset.py` запускает реальные модели и сохраняет результаты; отдельные регрессионные тесты без LLM.

**Открыто:** нет полноценного product funnel/обучающего эффекта, доли успешных достижений учеников, оценки персонализации с человеческой разметкой, устойчивости к атакующим формулировкам, стоимости/времени для каждого узла в агрегированных дашбордах. Проверку correctness нельзя заменить judge одной маленькой LLM.

### 2.8 Observability

**Исправлено:** при запросе пишутся обезличенные события API, на каждом узле пишется span с `trace_id`, duration, success; их можно сгруппировать в траекторию; логируется аномально медленная операция.

**НЕ закрыто по ТЗ:** централизованная система (Phoenix/Jaeger/Langfuse/LangSmith), реальная доставка алертов, выбор SLO и порогов с owner, корреляция токенов TTFT/TPS с узлами, долговременная система хранения метрик. Текущий JSONL — минимально наблюдаемый прототип, а не production observability.

### 2.9 Skills / Semantics / Documentation

**Исправлено:** два содержательных `SKILL.md` с ограничениями и инструментариями, подключены к LLM-подсказкам; убрано молчаливое отсутствие prompt-файла. Но в ТЗ также ожидаются семантически наполненные файлы концептуальных правил агента (SOUL-like), которые должны быть согласованы с кодом и пройти тесты. Есть черновик C4-флоу, но не 7 полноценно согласованных C4 диаграмм.

### 2.10 Тесты / CI / Окружение

**Проверено здесь:** Python compileall; 36 офлайн-тестов, в том числе API, маршруты, профили, запуск SymPy отдельным процессом. Система тестирования в моей среде **не содержит установленного LangGraph**, поэтому во время unit-проверки использовался минимальный test shim для компиляции графового API. Это не тест реального LangGraph или Ollama. Реальные e2e необходимо прогнать в вашей `.venv` на Windows; результаты нельзя выдумывать.

**Открыто:** GitHub Actions нужно прогнать на обновлённых requirements; на Windows проверить `subprocess` timeout/кодировку; поднять FastAPI и проверить `/api/v1/agent`, `/api/v1/check-solution`; выполнить 42 реальных генерации; добавить негативные тесты на неверные математические ответы и инъекции.

## 4. Рекомендуемая очерёдность работы (без маскировки недостатков)

1. **Сразу:** проверить новую копию в отдельной Git-ветке на Windows, включая `pip install`, `pytest` и `audit_dataset_routes`; записать коммиты.
2. **День 1:** E2E 3 случая на Ollama, затем 42 по датасету; ручной вердикт по correctness и relevance; зафиксировать regressions.
3. **День 2:** разделить математический структурный ответ и свободное объяснение, валидировать структуру/корни SymPy; не использовать LLM as sole oracle.
4. **День 3:** спроектировать аутентификацию учеников, стабильные ID, авторизацию данных и разделение сессий.
5. **День 4:** определить sandbox уровень среды и реально поднять ограничения; зафиксировать тест тайм-аута и resource isolation.
6. **День 5:** реализовать честную среднесрочную актуализацию памяти; подтвердить двух-/трёхуровневый дизайн; интегрировать RecSys, если заявляется в ТЗ проекта.
7. **День 6:** интегрировать наблюдаемость со стеком (например, Phoenix + OTel), реальные алерты и дашборды, добавить product evals.
8. **День 7:** финальная архитектура (7 C4 + sequence), демонстрация, устные ответы о трёх моделях, RAG vs temporal memory, validators, latency, limits.

## 5. Что НЕ делали и почему

- **Не запускали Ollama и не утверждаем 42 корректных ответа:** локальных моделей в среде аудита нет; роутинг ≠ качество.
- **Не выдаём subprocess за полноценный sandbox:** нет OS isolation и resource quotas.
- **Не выдумываем реализованную L3 memory / frontend / identity provider / agent skill runtime:** код должен подтверждать заявления.
- **Не удаляли проверяемые экспериментальные CSV, результаты и Two-Tower:** их сохранение важно для доказательности, даже если они не интегрированы.
- **Не меняли исходный пользовательский архив:** весь код в отдельной папке с новой копией.

## 6. Команды проверки в локальной копии пользователя

```powershell
python -m pip install -r requirements.txt
python -m pytest -q -m "not slow"
python -m scripts.audit_dataset_routes
python scripts/run_graph_dataset.py --limit 3
python -m uvicorn src.api.main:app --reload
```

**Ожидания:** unit-тесты должны проходить; `route_audit.csv` — 42 совпадения на имеющемся датасете. Ответы LLM, статусы и длительности могут отличаться по машине. Перед слиянием в `main` нужно проверить полный граф, отдельное семейство валидатора, OS-специфику worker и безопасность доступа к данным.
