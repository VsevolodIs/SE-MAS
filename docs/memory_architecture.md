# Организация памяти TutorFlow AI — актуализация 10.11.2026

## Фактическое состояние после ревью

1. **L1 (short-term)**: `AgentState.chat_history` и `session_messages` в SQLite. Для *внутренних* запросов с `session_id` координатор читает последние 8 реплик, генератор добавляет до 6 предшествующих реплик как отдельный недоверенный контекст. Последний пользовательский запрос и ответ сохраняются после выполнения. История не выдаётся через публичный API до реализации аутентификации.
2. **L2 (профиль ученика)**: `students`, `lessons`, `assignments`; при поиске профиля сохраняется явно заданный уровень/слабые темы. Нет автоматического обновления компетенций и полноценной авторизации к истории по student_id.
3. **L3**: семантическая долговременная память, темпоральные графы, политика актуализации и разрешения конфликтов ещё не реализованы.

**Предупреждение:** исходная документация ниже содержит элементы проектного плана. Не выдавать за демонстрируемые механизмы. Исходное описание проверяло старый архив, поэтому оно частично историческое.

## 3. Целевая трёхуровневая схема

| Уровень | Данные | Хранение/доступ | Статус |
|---|---|---|---|
| **L1 — рабочий контекст (short-term)** | текущий запрос, промежуточные решения, маршрут графа, последние реплики | `AgentState` + выборка из `session_messages` | Частично реализовано; историю нужно реально включать в контекст LLM |
| **L2 — профиль и история обучения (medium-term)** | класс, уровень, слабые темы, успешность по темам, последние уроки | SQLite, таблицы `students`, `lessons`, `assignments` | Частично реализовано; требуется механизм обновления компетенций |
| **L3 — долговременная семантическая память (long-term)** | устойчивые предпочтения, подтверждённые знания, конспекты прогресса, релевантные учебные материалы | Предлагается отдельный индекс фактов/документов с поиском и источниками | **Не реализовано в просмотренном архиве** |

Разделение уровней необходимо не для количества хранилищ как такового: L1 ограничивает контекст запроса, L2 обеспечивает точные структурированные факты, а L3 позволяет находить информацию по смыслу на длительном горизонте.

## 4. Актуализация и предотвращение ошибок памяти

**Предлагаемый алгоритм:**

1. При новом запросе получать последние сообщения по `session_id` и проверенный профиль ученика.
2. Использовать в контексте только сведения, относящиеся к текущей теме; различать сообщение ученика, вывод LLM и проверенный факт.
3. После проверки задачи сохранять результат и обновлять оценку освоения темы **только по достоверному вердикту**. Ошибка парсера или `manual_verification_required` не должна ухудшать уровень ученика.
4. Повторяющиеся подтверждённые наблюдения консолидировать в профиль; спорные данные помечать как непроверенные.
5. Для L3 хранить происхождение факта, дату, версию и дату последней проверки; при конфликте отдавать приоритет свежим проверенным данным, а не старым пересказам модели.
6. Предусмотреть исправление и удаление ошибочных данных ученика, а также минимизацию сохраняемой персональной информации.

**Важно:** пункты 2–6 — проектные рекомендации, а не описание уже существующих функций.

## 5. Почему недостаточно обычного RAG

Классический RAG полезен при поиске учебных материалов и фактов из документов, но сам по себе не решает задачу персональной памяти: он не гарантирует обновления оценок знаний, разрешения противоречий, контроля источников и устойчивого состояния между занятиями. Кроме того, поиск похожего текста не эквивалентен точной выборке уровня ученика и его результатов.

Поэтому для TutorFlow AI предпочтительна **гибридная архитектура**: структурированные факты и события обучения в SQLite, оперативная история в состоянии графа, а семантический индекс — только при появлении реальной потребности в поиске по большому объёму материалов и наблюдений.

Рассмотренные альтернативы:

- **Только история сообщений:** простая интеграция, но растёт контекст, сложно поддерживать достоверность и исправлять устаревшее.
- **Только векторный RAG:** удобный semantic search, но слабый контроль версий и точных полей профиля.
- **Graphiti / граф знаний:** полезен для временных связей и пересмотра фактов, но требует дополнительных компонентов и усложняет небольшой прототип.
- **Mem0 / LangMem:** могут автоматизировать извлечение долговременных фактов, но добавляют стоимость инференса и риск запоминания непроверенных утверждений; нуждаются в evals.
- **SQLite + выборочный retrieval:** воспроизводимый и простой для локального MVP, но хуже масштабируется для смыслового поиска по большим материалам.

## 6. Ограничения и следующие шаги

В текущем состоянии не подтверждены: L3, поиск по семантической памяти, обновление профиля после выполнения заданий, TTL/архивация истории, разрешение конфликтов и гарантированное включение истории в промпты. Для завершения обязательного требования необходимо либо реализовать отсутствующие уровни, либо согласовать более ограниченный объём и продемонстрировать хотя бы два фактически работающих уровня с актуализацией.
