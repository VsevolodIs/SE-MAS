# Изоляция математических вычислений в TutorFlow AI

## 1. Цель и границы доверия

TutorFlow AI получает текстовые математические выражения от пользователя и обрабатывает их с помощью SymPy. Такая строка — **недоверенный ввод**: в ней могут содержаться не только уравнения, но и синтаксические конструкции, некорректные данные, ресурсоёмкие выражения или намеренные попытки злоупотребления парсером.

В преподавательском ТЗ требуется рассмотреть контейнеры, runtime sandbox, VM/MicroVM и другие варианты изоляции, выбрать подходящий и обосновать риски. **Наличие файла с именем `sandbox.py` само по себе не означает изолированного исполнения.**

## 2. Фактическая реализация в просмотренном архиве

В `src/tools/sandbox.py` реализованы:

- предобработка строк (`^` → `**`, десятичная запятая, неявное умножение, простые проценты);
- проверка подстрок по списку `FORBIDDEN_KEYWORDS`;
- извлечение отношения, решение уравнений/неравенств и вычисление выражений через `sympy.sympify()`;
- выполнение вычислений внутри `ThreadPoolExecutor(max_workers=1)`;
- запрос результата с ограничением `timeout_sec` (по умолчанию 3 секунды) и возвратом статусных кодов.

Это **логическая обёртка над математическим инструментом**, но не полноценная граница безопасности. Рабочий поток разделяет память, процесс, файловую систему и привилегии основного API. Отмена `future.result(timeout=...)` не принуждает SymPy остановиться; выход из контекстного менеджера executor может ждать завершения задачи. Поиск запрещённых подстрок не является надёжной защитой интерпретатора выражений. `sympy.sympify()` нельзя считать безопасным для произвольных недоверенных строк.

**Итог аудита:** безопасное исполнение недоверенных математических выражений в текущем архиве не подтверждено. Этот документ не должен утверждать обратного.

## 3. Модель угроз

| Угроза | Последствия | Требуемый контроль |
|---|---|---|
| Вредоносная строка, передаваемая парсеру | Неожиданное вычисление / нарушение безопасности | Строгий whitelist грамматики, безопасный парсер, отдельный процесс |
| Бесконечное/долгое вычисление | Зависание worker/API | Внешний watchdog с принудительным завершением процесса |
| Чрезмерное потребление RAM/CPU | Отказ в обслуживании | Лимиты CPU, памяти, времени, количества параллельных задач |
| Доступ к сети или файлам | Утечка данных, расширение воздействия | Запрет сети, ограниченная файловая система и полномочия |
| Ошибка разбора обычного текста | Ложное обвинение ученика в ошибке | Отдельный статус `unsupported` / `manual_verification_required` |
| Prompt injection в условии | Перехват инструкций агента | Разделение инструкций и пользовательских данных, независимая валидация |

## 4. Сравнение вариантов

| Вариант | Плюсы | Ограничения | Решение |
|---|---|---|---|
| Python thread | Дёшево и просто | Нет изоляции, нельзя принудительно безопасно остановить вычисление | Не подходит как sandbox |
| Отдельный процесс ОС | Можно завершить по таймауту, отделяет адресное пространство | Нужны ограничения привилегий, памяти и файловой системы | Минимальный обязательный шаг |
| Docker-контейнер | Воспроизводимые зависимости и ограничения ресурсов | Общее ядро ОС; типовой контейнер без hardening — не строгая песочница | Допустим как один из слоёв, но не единственная мера |
| gVisor / Kata Containers | Усиление границы выполнения по сравнению с обычным контейнером | Более сложная настройка и накладные расходы | Кандидаты при наличии подходящей среды |
| MicroVM / Firecracker | Более сильная изоляция на уровне виртуализации | Сложная инфраструктура, дорого для учебного прототипа | Альтернатива для высокорискового выполнения |
| E2B / специализированный sandbox | Готовые механизмы изоляции и жизненного цикла | Дополнительные зависимости, сеть/стоимость или ограничения провайдера | Сравнивать при наличии доступа |

**Предлагаемое проектное решение:** строгий ограниченный синтаксис математических выражений + отдельный worker-процесс с лимитами CPU/RAM/времени, запретом сети и минимальными правами. Если есть подходящая платформа, усилить процесс контейнерной/виртуализированной изоляцией. Реальный выбор нужно согласовать с окружением запуска и экспериментально проверить. Для локальной разработки на Windows нельзя автоматически считать Linux-механизмы `seccomp`/`rlimit` доступными без соответствующего окружения.

## 5. План перехода от текущей обёртки к реальной изоляции

1. Ограничить принимаемую грамматику: числа, разрешённые переменные, скобки, арифметические операции, сравнения; запретить произвольные имена, атрибуты и вызовы функций.
2. Разделить API и вычислитель на разные процессы; передавать ограниченный структурированный запрос, а не исполняемый Python-код.
3. Запускать worker с минимальными полномочиями, без доступа к секретам API и без исходящего сетевого соединения.
4. На уровне ОС или среды исполнения ограничить время, память, CPU и число одновременных задач; по таймауту уничтожать worker.
5. Возвращать типизированные статусы `success`, `invalid_input`, `unsupported_format`, `timeout`, `resource_limit`, `internal_error`.
6. Не приравнивать техническую ошибку парсера к неверному решению ученика; передавать запрос на безопасную дополнительную проверку.
7. Проверить тестами обычные уравнения, ОДЗ, неравенства, вложенные выражения, длинные входы и выход за лимиты.

**Статус:** это план доработки, который должен реализовать ответственный за backend; в приложенном архиве перечисленные меры не обнаружены.
